# 藍圖：「讓人想繼續走」的小試作

日期：2026-11-17。作者：Fable。讀者：接手設計的 Opus。狀態：設計說明，user 尚未說開工。

這份檔寫的是意圖、邊界與每個試作要回答的問題。房間長什麼樣、參數取多少、用哪種實作，由你判斷。你認為這裡的做法不對時，照〈哪些能改〉處理。

## 為什麼做

工作臺目前只回答「畫面像不像參考圖」。封存的調查（`archive/docs/research/c2-player-voice.md` 第 2.5、2.6、5 節）顯示這只是入場條件：

- 同類遊戲最常見的負評是「只有走路、很空」。
- 不滿意的玩家多半在開頭就離開。
- 「沒有怪物、不嚇人」是賣點，破壞它會被玩家點名。

user 不確定該提升玩家的哪一面，所以先用小試作找答案。「想繼續玩」拆成三層：

| 層 | 玩家心裡的問題 | 對應的試作 |
|---|---|---|
| 每一秒 | 走起來、聽起來舒不舒服 | 水裡移動、聲音 |
| 每一間 | 想不想走進下一間 | 下一間的拉力、尺度對比 |
| 每一輪 | 為什麼走完、為什麼再來 | 死路的回報、拍照 |

user 已定：玩家的目的是拍照（找到好畫面、拍下來），不設失敗條件；一輪多長等走過再定（`DECISIONS.md` 2026-11-17）。

## 哪些能改

| 類別 | 內容 | 你要改時 |
|---|---|---|
| 固定 | 每個試作只問 user 一句話；變體最多三個；user 親自走過才算有答案；不加怪物、驚嚇、失敗條件；遊戲本體（`js/`）不動；產出必須仍能打包進單一 HTML | 先問 user |
| 你決定 | 房間的形狀與大小、參數值、實作方式、試作的先後、要不要合併兩個試作、那一句話的措辭 | 直接做，回報時說選了什麼、為什麼 |
| 要回頭問 | 試作的結果互相矛盾；某個試作需要動到暫停中的東西（水下外觀、完整的移動手感、佈局生成器）；你認為某個試作問錯了問題 | 用問答工具問，附你看到的事實 |

「一句話」是這份藍圖最重要的限制。它的用途是防止試作變成多輪猜外觀：`STATE.md` 的契約寫明 agent 不靠多輪變體猜，user 兩個 session 內調不出來就要重新審視方向。

## 每個試作共通的形狀

1. 一個或一組試作房間，加上各變體的接觸表設定，讓 user 用一個網址就能走。
2. 給 user 的說明不超過五行：開哪個網址、走哪裡、走完回答哪一句。
3. user 的回答記進 `DECISIONS.md` 一行。回答改變了契約或下一步時，改 `STATE.md`。
4. 試作房間與零件各自獨立，能單獨回退。

**變體怎麼交付。** 檢視器用一份接觸表設定決定載入哪個房間與哪四組預設（光、水、材質、手感）。一個變體就是一份設定檔，user 換網址裡的名字就能切換。側邊欄的「保留成 A、按住看 A」只能比外觀預設，不能比房間。

**變體之間只差一樣。** 光、水、材質用同一組預設，選目前最好的那一組並寫在說明裡。這些外觀都還沒被 user 接受；畫面不好看本身就會讓人不想走，所以每個結論都要註明是在哪一組外觀下得到的。

**怎麼走。** 請 user 每個變體至少各走兩次、可以來回切換，再回答。先走的那個容易佔便宜。說明裡寫清楚用什麼裝置、橫向還是直向、聲音試作要不要戴耳機。

**最多兩輪。** 一輪做出來，一輪依 user 的反應調整。第二輪之後 user 仍答不出那一句，就停下回報看到了什麼，不做第三輪。這對應 `STATE.md` 的停損訊號。

**給 user 之前你自己要先確認的。** 每個變體用出圖腳本各出一張圖，確認變體之間真的看得出差別；跑一次碰撞檢查。聲音與手感出不了圖，改成寫下你實際聽到、走到的差別。

**user 沒回答。** 那一句寫進 `QUESTIONS.md`，依賴它的後續決定不做。

**受測的人只有 user。** user 知道這個專案的設計，對「想不想繼續走」的反應和第一次玩的人不同。這些試作能排除明顯不成立的做法，不能證明新玩家會留下來。試作一與試作六最受影響；有結果之後，向 user 提出要不要找一位沒看過的人各走一次。

「成立」的標準不是做得多完整，而是 user 答得出那一句話。答不出來通常代表變體之間差異太小，或同時變了兩樣東西。

## 試作

每個試作寫四件事：意圖、最少要有什麼、user 回答的一句、已知的坑。

### 一、下一間的拉力

- **意圖**：找出什麼樣的門口讓人想走過去。假設是「只露出一部分」比「一眼看穿」更有拉力。這是假設，試作就是要驗它。
- **最少要有什麼**：兩到三間相接的房間，同一組房間做兩種相接方式：一種看得穿，一種只露出光、水面或柱列的一角。
- **那一句**：「站在門口時，哪一種讓你比較想走過去？」
- **坑**：這個試作依賴連接口（元件計畫新增的那一項）與「接兩三間走一遍」那一步。在那之前可以用一個大房間以牆隔成幾區來近似；近似版本的結論要標明是近似。user 的原則是相接看流動性、不設固定比例，所以結論不可寫成「幾成的門要遮」，只能寫成「什麼情況下露多少」這類條件。「漏出來的光」怎麼表現取決於還沒選定的光照方法；光照選定前做的版本，結論只對形狀與視線成立，不對光成立。

### 二、尺度對比

- **意圖**：確認「走進大空間的那一刻」是不是這個遊戲的主要感受來源。調查中玩家稱讚的原話是在大房間裡覺得自己很小。
- **最少要有什麼**：同一個大廳，前面分別接窄道與另一個大廳。
- **那一句**：「走進大廳那一刻，哪一種順序有感覺？」
- **坑**：可以和試作一共用房間，但一次只變一樣。相機高度與視角寬度會強烈影響尺度感。目前是眼高 1.6 公尺、視角 70 度，沒有紀錄顯示 user 決定過這兩個值；試作中固定不動，並在回報中寫出用的值。手機直向與橫向看到的寬度差很多，同一個大廳的感受會不同：指定 user 用哪一種，兩種都重要時各走一次。

### 三、水裡移動

- **意圖**：找出在水裡的移動是負擔還是樂趣。這類遊戲裡最接近「好玩」的部分是和水的互動。
- **最少要有什麼**：一個有幾種水深、能走進走出的房間，兩到三組在水中表現不同的手感預設。現有的手感測試房有 0.3、0.6、0.9 公尺三種深度與坡道，可以當起點。
- **那一句**：「哪一組讓你想多待在水裡？」
- **坑**：移動手感、入水回饋、水下外觀都在暫停清單。user 只開放「水中移動的小試作」。所以這裡只調水中的移動參數；不做水下畫面、不做入水的畫面或聲音效果、不重做陸上手感。若你判斷沒有游泳或下潛就答不出那一句，這屬於〈要回頭問〉。
- **三個要先知道的事實**：
  - 水深現在完全不影響移動。要有「在水裡不一樣」的感覺，至少要讓那個固定回傳 1 的函式開始作用。那正是暫停清單裡的涉水減速；user 開放的小試作涵蓋它，但做出來的是試作，不算那一項完成。
  - 身體貼地走，所以水比眼高深時，鏡頭會直接沒入水中，看到的是暫停中、沒做過的水下畫面。試作房間的水深要低於眼高，或另外處理；不要讓 user 在這個試作裡掉進水下。
  - 手感預設會檢查十個鍵是否齊全。新增水中的參數時，三組現有預設與檢查都要一起補，鍵名只增不改。
- **可以考慮但不必做的方向**：水越深越慢、起步與停下在水裡變鈍、晃動的幅度與節奏在水裡改變。選哪幾樣由你決定；一次比較只變一樣。

### 四、聲音

- **意圖**：確認聲音能不能讓空間變大、變空。聲音目前不在任何清單裡。
- **最少要有什麼**：同一個房間，無聲與有聲各一版。有聲版至少有腳步與隨空間大小改變的殘響；水聲可選。
- **那一句**：「有聲的版本，空間有沒有變大或變空？」
- **坑**：遊戲必須打包成單一 HTML，音訊檔比房間資料大得多。先用程式合成的聲音，不用錄音檔；若合成的聲音不足以回答那一句，再回頭問。手機瀏覽器通常要使用者先碰一下畫面才允許出聲，這點我沒查證，動手前查當前的文件。
- **現成可用的資料**：移動器已經有走路晃動的相位，可以拿來對腳步的節拍；有水深，可以分辨乾地與水中；有「這一幀入水或出水」的旗標。房間檔有格子大小與天花板高度，房間的體積算得出來，殘響的長短可以由體積決定，不必每個房間手填。
- **入水的水花聲**算不算暫停中的「入水回饋」，我沒有把握。要做之前問 user。
- 手機喇叭幾乎聽不出殘響。說明裡請 user 戴耳機，並記下 user 實際用什麼聽。

### 五、死路與支線的回報

- **意圖**：user 要有分支與死路。調查中有遊戲因「太多沒意義的死路」被負評。要找出走到盡頭給什麼才值得。
- **最少要有什麼**：三條支線，盡頭分別是：一個別處看不到的景、一間只在支線出現的房間、什麼都沒有（對照組）。
- **那一句**：「哪一條讓你覺得走過來值得？」
- **坑**：對照組不可省，沒有它就不知道回報有沒有作用。三條支線的長度要相同：走回頭路的時間本身就是代價，長度不同就分不出是回報的差別還是路程的差別。這個試作和拍照是同一件事的兩面，適合排在拍照之後。

### 六、拍照

- **意圖**：確認「拍照當目的」會不會改變 user 走路的方式。這是 user 選定的玩家目的，其他試作的結論都要回到它身上。
- **最少要有什麼**：按一下就把當前畫面存成圖，並且當場看得到剛拍的那一張。不做相簿、濾鏡、分享。看不到成果就沒有回饋，user 無從判斷自己會不會想再找一個角度。
- **那一句**：「走的時候，你會不會開始找角度？」
- **坑**：手機上存圖的方式和桌機不同，我沒查證。拍照讓「畫面在任何角度都撐得住」從風險變成需求；試作中若發現某些角度明顯穿幫（水面、反射、窗列的掠角），記下來，那是元件驗收要補的，不在這個試作裡修。
- **幾個容易漏的地方**：手機沒有鍵盤，要有畫面上的按鈕，而且拍下來的圖裡不能有按鈕、數據或側邊欄。拍照是要進遊戲的功能，所以它不可依賴側邊欄、接觸表、伺服器這些不進遊戲的部分（`STATE.md` 的工作臺定位）。聲音也一樣。
- 觸控轉視角若太粗，user 會因為對不準而放棄找角度，結論會被操作手感污染。先確認能穩定對準再請 user 走。

## 建議的先後

這是建議，不是規定。

1. **拍照、水裡移動、聲音**：只需要單一房間，現在的工作臺就能做，彼此不相干。
2. **下一間的拉力、尺度對比**：要等連接口與「接兩三間走一遍」。
3. **死路的回報**：要有拍照，也要有相接的房間。

第一批裡有三個試作在手機上的行為和桌機不同。至少請 user 在手機上各走一次。

開始任何試作之前，先請 user 用手機開一次現有的房間，確認畫面出得來。多數玩家用手機，而工作臺從未在手機上確認過能不能正常顯示；這件事不通，後面的試作都要改做法。

**哪些試作會碰同一批檔案。** 水裡移動動移動器與手感預設；拍照動檢視器的入口；聲音是新的獨立部分，但要讀移動器的狀態；拉力與尺度對比動房間檔格式與檢視器的載入。要同時交給兩個 builder 時，拍照與水裡移動不重疊，可以平行；其餘排先後。

## 結果會改變什麼

| 試作的答案 | 影響 |
|---|---|
| 露一部分的門口比較有拉力 | 連接口的設計要能表達「露多少」；房間設計時留意門口看出去的畫面 |
| 尺度對比有感覺 | 組裝房間時相鄰房間的大小差是要考慮的條件；相機高度與視角寬度要正式定下來 |
| 水裡移動是樂趣 | 向 user 提出重啟移動手感與入水回饋；房間設計增加水的比重 |
| 水裡移動是負擔 | 深水區改成看的不是走的；不必重啟那兩項 |
| 聲音有效 | 聲音進元件計畫；要決定合成還是錄音，以及單一 HTML 的大小預算 |
| 支線要有回報才值得 | 組裝器不可隨機長出空的死路；每條支線要有一個回報 |
| 拍照改變了走路方式 | 每個房間至少要有一個站上去就成立的畫面，成為房間的驗收條件之一 |
| 拍照沒有改變什麼 | 向 user 回報，玩家的目的要重新討論 |

右欄每一條都是「向 user 提出」，不是自動生效。

## 不做的

存檔、選單、完整的一輪流程、起點到出口的主線邏輯、佈局生成器、水下外觀、任何會嚇人的東西。工作臺只回答「這個東西成不成立」。

## 交給 builder 之前

- user 說開工才開。
- 實作交給 builder 時照 `docs/procedures/delegation.md`。這份藍圖是給你判斷用的；給 builder 的交接要另寫，寫成它能直接照做的步驟。
- 新增物件類型或參數鍵時遵守「只增不改名」。
- 每個試作做完跑 `node workbench/feel-check.mjs`。
