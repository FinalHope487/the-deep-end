# 程序：驗證與測試

觸發：要改任何程式或測試。
讀者：agent。

把測試視為風險保險，依「變動頻率」與「出錯代價」決定驗證手段，不盲目追求 100% 覆蓋率：
- **應寫自動化測試範圍**：完成＝有一段先前會失敗、現在會通過的測試
- **免寫自動化測試範圍**：完成＝既有測試全綠，且附執行輸出或狀態證據

## 驗證原則與執行

- 執行測試前，先從專案的指令入口找出既有測試指令並原樣使用：npm／pnpm scripts、Makefile、justfile、Taskfile、`pyproject.toml`／`tox.ini`／noxfile、Cargo、Gradle／Maven、CI 設定檔、README 的測試段落
- 不自己拼底層指令；找不到入口才用工具鏈預設指令
- 回報與 commit message 記錄入口指令與實際輸出
- 只跑涵蓋本次改動的測試。工作臺：`STATE.md`〈測試〉。遊戲本體：跑哪一層、何時跑慢速層、新測試放哪層照 `docs/testing.md`

## 什麼時候寫測試、什麼時候不寫

動手前依此表決定測試策略：

| 程式碼特性 | 變動頻率 | 出錯代價／除錯難度 | 測試策略 |
|---|---|---|---|
| **Functional Core（核心演算法與純資料轉換）** | 低 | 極高（肉眼難抓、算錯全盤皆輸） | **重度單元測試 + 邊界測試**（涵蓋正負數、零、跨越邊界、固定 Seed 確定性、序列化對稱） |
| **業務邏輯與狀態機** | 中 | 高（狀態錯亂、資料損毀） | **針對公開行為寫單元／整合測試** |
| **Imperative Shell（外部 I/O、資料庫、API、UI 接線）** | 低～中 | 高（斷線或改版即崩潰） | **只寫少量契約測試／煙霧測試／端到端測試**，確認整條路接通即可；不做重度 Mock |
| **UI 視覺表現、數值手感微調、初期 Prototype 探索** | 極高 | 低（歪掉一眼看出、隨時可能迭代） | **不寫自動化測試**；使用者要求時再補關鍵測試 |

## 架構切分與外部邊界

- 實作優先切分為 **Functional Core（純函數核心）** 與 **Imperative Shell（命令式外殼）**
- 單元測試集中在純函數核心（輸入 A 必得輸出 B，零 I/O、零 UI 框架、零 Mock）
- 若為測 5 行邏輯需寫 50 行 Mock（模擬資料庫、計時器、引擎環境或網路）：立刻停手，先重構將純邏輯抽離成獨立純函數，只測該純函數
- 需要驗證 Imperative Shell 整條路接通時，打在真實邊界（網頁＝真瀏覽器打真伺服器；CLI＝子程序執行真執行檔驗 argv／stdout／exit code；函式庫＝import 公開 API；服務＝走真網路層），斷言打在角色、狀態、Schema，不做像素或視覺動畫比對

## 寫測試時

1. **測契約（What），不測實作細節（How）**：斷言公開輸入與最終輸出（例：結構化解析與業務狀態一致），禁止斷言內部私有函式呼叫次數或快取陣列長度
2. **無標準答案時測不變量（Invariants）**：面對生成式演算法、視覺化計算或 AI 輸出，不寫死特定常數；改測系統底線（不拋 Exception、不產生 NaN／無限大、相鄰邊界合法、輸出符合 Schema、極端條件在時限內跑完）
3. **依改動性質決定測試策略**：
   - **全新摸索與 POC 實驗**：免寫自動化測試，先求走通流程；驗收以執行輸出與手動調試日誌為準
   - **結構調整與架構重構**：動手前以既有公開行為為基準補上防護測試，再改內部實作；不改公開契約
   - **缺陷修復（Bug-Driven）**：先確認既有測試通過，接著寫一條重現該 Bug 的最小失敗測試（確認紅的原因正是缺陷所在），修復後該測試變綠
4. 看測試數字，不只看綠；沒實際跑過的數字標明是預期值
5. 條件式 skip 在 CI 等嚴格驗證環境須明確標註原因；本地開發缺件可有條件跳過

## 下結論時

- 任何「沒問題／可以了／檢查過了」須附 `檔案:行號` 或指令輸出；沒有證據的審查視為沒發生，重做
- 回報「這個 bug 不存在」須附：程式碼關鍵位置（`檔案:行號`）、既有測試涵蓋該邏輯的執行輸出，並從資料流說明為何該邊界條件已受防護

## 測試失敗時

基於 Log、堆疊追蹤與原始碼定位根本原因，禁止盲目假設或加入靜默 catch 掩蓋問題。
若屬於重複性或已知環境陷阱，查閱並更新 `SOP/` 的對應記錄。
